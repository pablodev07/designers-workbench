# UI Health Fix

Automatically applies fixes for issues identified by the `/ui-health-check` skill. Implements solutions following Salesforce, LWC, SLDS, WES, and Slack design system best practices.

## What this skill does

This skill reads the health check report generated by `/ui-health-check` and automatically applies code fixes for issues marked as "auto-fixable". It:

1. **Parses the health check report** to identify fixable issues
2. **Applies fixes** using Salesforce and design system best practices
3. **Validates changes** to ensure fixes don't break existing functionality
4. **Creates detailed commit messages** documenting what was fixed
5. **Generates a summary report** of all changes made

## Safety Features

### Preview Mode (Default)
By default, the skill runs in **preview mode** - showing you exactly what will be changed before making any modifications:

```bash
/ui-health-fix --preview
```

This displays:
- Files that will be modified
- Exact before/after code diffs
- Explanation of each fix
- Confidence level for each change

### Confidence Levels
Each fix has a confidence level indicating automation safety:

- **High (95-100%)**: Safe to auto-apply (e.g., adding ARIA labels, replacing deprecated classes)
- **Medium (75-94%)**: Likely safe but may need review (e.g., design token substitution with color mapping)
- **Low (<75%)**: Requires manual review (e.g., complex logic refactoring)

By default, only **High confidence** fixes are applied in auto mode.

## How it works

### Phase 1: Report Analysis
- Loads the latest health check report (or specified report ID)
- Identifies all auto-fixable issues
- Groups fixes by file and component
- Sorts by confidence level

### Phase 2: Fix Application
Applies fixes using specialized fixers:

**Accessibility Fixes**
- Adds ARIA labels, roles, and attributes
- Adds keyboard event handlers (onkeydown, onkeyup)
- Inserts screen reader text (slds-assistive-text)
- Fixes heading hierarchy
- Adds alternative text to images and icons

**Design System Fixes (SLDS/SLDS2)**
- Replaces hardcoded colors with SLDS design tokens
- Updates deprecated class names (SLDS1 → SLDS2)
- Adds proper SLDS utility classes
- Fixes spacing using SLDS spacing scale
- Replaces custom icons with SLDS icons

**Design System Fixes (WES - Web Experience System)**
- Suggests WES component replacements for custom implementations
- Replaces hardcoded values with WES design tokens (--wes-*)
- Applies WES component patterns (wes-button, wes-card, wes-icon)
- Fixes styling to use WES foundation and styling hooks
- Ensures customer-facing brand consistency

**Design System Fixes (Slack)**
- Replaces hardcoded colors with Slack design tokens (--sds-*)
- Applies Slack component patterns
- Fixes spacing to align with 4px grid
- Updates to Slack typography tokens

**LWC Best Practices Fixes**
- Removes unnecessary @track decorators
- Adds error handling to @wire adapters
- Fixes event handling patterns (CustomEvent)
- Adds proper lifecycle hooks
- Fixes import statements
- Removes console.log statements

**Performance Fixes**
- Optimizes template directives (if:true → if:false where appropriate)
- Adds getters for computed properties
- Fixes reactive property assignments
- Adds event listener cleanup in disconnectedCallback

**Testing Fixes**
- Generates basic Jest test scaffolding
- Adds missing test cases for @api properties
- Adds accessibility test assertions

### Phase 3: Validation
After applying fixes:
- Runs ESLint to ensure no new linting errors
- Compiles LWC components to verify syntax
- Runs existing Jest tests to ensure no regressions
- If validation fails, changes are rolled back automatically

### Phase 4: Reporting
Generates a fix summary:
- Total issues fixed
- Files modified
- Changes by category
- Any issues that couldn't be auto-fixed (manual intervention needed)
- Next steps

## Usage

### Preview Mode (Recommended First Step)
```bash
/ui-health-fix --preview
```
Shows all proposed changes without modifying files.

### Apply All High-Confidence Fixes
```bash
/ui-health-fix --auto
```
Automatically applies all high-confidence (95%+) fixes.

### Apply Specific Category
```bash
/ui-health-fix --category=accessibility --auto
```
Fix only accessibility issues automatically.

### Apply Specific Component
```bash
/ui-health-fix --component=c-notification-panel --auto
```
Fix issues in a specific component only.

### Include Medium Confidence Fixes
```bash
/ui-health-fix --auto --min-confidence=75
```
Apply fixes with 75%+ confidence (includes some medium-confidence fixes).

### Fix Specific Issue
```bash
/ui-health-fix --issue=CRITICAL-001 --auto
```
Fix a single specific issue by ID.

### Dry Run with Validation
```bash
/ui-health-fix --preview --validate
```
Preview changes AND run validation checks to ensure fixes won't break anything.

### From Specific Report
```bash
/ui-health-fix --report=uhc-20260625-143210 --auto
```
Apply fixes from a specific health check report.

## Rollback Support

If something goes wrong or you want to undo the changes:

```bash
/ui-health-fix --rollback uhf-20260625-144530
```

This will:
- Revert all changes made by the specified fix session
- Restore files to their pre-fix state
- Provide a summary of what was rolled back

## Safety Guarantees

✅ **Always validates** changes don't break compilation or tests
✅ **Automatic rollback** if validation fails
✅ **Detailed logging** of all changes made
✅ **Git commits** with detailed messages (can be easily reverted)
✅ **Preview mode** available for all operations
✅ **Confidence scoring** prevents risky automated changes

## Best Practices for Using This Skill

1. **Always preview first**: Run `--preview` before `--auto`
2. **Start with critical issues**: Use `--severity=critical` first
3. **Test incrementally**: Fix one category at a time
4. **Review commits**: Check the diff after auto-fixes
5. **Keep tests updated**: Run full test suite after fixes
6. **Manual review for medium confidence**: Review 75-94% confidence fixes before applying

## Limitations

This skill **cannot** automatically fix:
- Issues requiring business logic understanding
- Complex architectural refactoring
- Test case creation (only scaffolding)
- Storybook story content (only structure)
- Performance issues requiring algorithm changes
- Issues with <75% confidence without explicit flag

These issues will be flagged for manual intervention with guidance.

## When Auto-Fix Isn't Enough

Some issues require human judgment or design expertise. If you encounter:

- Issues marked as "Requires manual intervention"
- Medium-confidence fixes you're unsure about
- Design system questions (SLDS vs Slack patterns)
- Complex accessibility requirements
- Architectural or performance refactoring
